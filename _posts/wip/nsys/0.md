## Why is the CPU "slow" at issuing commands?

<img src="cpu-is-slow.png">

It isn't that the CPU is slow (it runs at GHz speeds); it is that PyTorch is a conversation, not a monologue.

Every time you write z = x + y, the CPU doesn't just "fire and forget." It has to perform a massive amount of administrative work before it can even tell the GPU to start:

Python Interpreter: It reads your Python code line-by-line (slow).

Dispatcher: It checks x and y. Are they Float32? Are they on the same device? Do they require gradients?

Shape Inference: It calculates what the shape of z will be.

Kernel Selection: It looks up the correct C++ function for "Add two Float32 CUDA tensors."

Launch: Finally, it pushes the command to the GPU queue.

The Cost: This administrative work takes ~5µs to 20µs per operation.

The Problem: If the GPU operation (the actual math) takes only 2µs (like in your vectorized_elementwise_kernel), the GPU finishes instantly and sits idle for 18µs waiting for the CPU to figure out the next step. This is the "CPU Gap" you see.

#### Why does the CPU time vary?
You asked why the latency isn't consistent. This variance comes from System Jitter and Python Internals:

Python Garbage Collection (GC): Every once in a while, Python pauses to clean up unused memory. This creates a random spike in CPU time.

OS Scheduling: Your OS (Linux/Windows) might interrupt your Python script to run a background task (like checking email or updating the UI), causing a 1-2ms delay.

Cold vs. Warm Cache: The first time you run a specific operation (e.g., aten::index with specific shapes), PyTorch has to do extra setup work (allocating memory, compiling a kernel). The second time, it might hit a cache, running faster.

## Backward vs Forward gaps

<img src="backward-vs-forward-gaps.png">

The Backward Pass almost always looks like a solid brick of GPU work (continuous utilization) compared to the "gappy" Forward Pass, and it is exactly because the map is already drawn.

### Forward

In PyTorch (Eager Mode), the Forward pass is Dynamic.

The Process: The CPU is not just telling the GPU what to do; it is effectively building the road while driving on it.

The Loop:

- Python Interpreter reads z = x * y.

- PyTorch creates a "Node" in memory to remember this operation (for the graph).

- PyTorch calculates shapes and strides.

- PyTorch dispatches the kernel.

The Bottleneck: The Python interpreter is slow. It often takes longer to decide to run a kernel than it takes to run the kernel. This creates the white gaps.


### Backward
When you call .backward(), you leave Python land and enter the C++ Autograd Engine.

The Graph: The computational graph (the sequence of operations) was fully constructed during the Forward pass. It exists as a linked list of C++ objects (GradFn).

The Execution: The C++ engine simply traverses this list.

It does not need to interpret Python code.

It does not need to check if/else logic (that was resolved in Forward).

It just looks at the dependency tree: "Input gradients ready? Fire kernel. Next."

The Result: The C++ dispatcher is incredibly fast—fast enough to keep the GPU command queue full, resulting in that "solid blue" timeline with no gaps.


## GPU Reductions & Atomics

#### **1. Memset: The "Reset Button"**
* **What is it?** A tiny kernel that writes a specific value (usually `0x00000000`) to a memory address.
* **When is it used?** Immediately before a **Reduction Kernel** (Sum, Mean, Norm).
* **Why?** The GPU reduction accumulates values into a target variable. If that memory address holds old "garbage" data (e.g., `55.2`), your sum will be wrong (`55.2 + Real_Sum`). Memset ensures the bucket is empty (`0.0`) before adding starts.


#### **2. Sequential Add vs. Atomic Add**
* **Sequential Add (Unsafe):**
    * **Steps:** 1. Read value, 2. Add local number, 3. Write new value.
    * **The Risk:** If Thread A and Thread B read `0` at the same time, they both write `1`. One update is lost (Result: `1` instead of `2`). This is a **Race Condition**.
* **Atomic Add (Safe but Costly):**
    * **Mechanism:** It locks the memory address. The hardware guarantees `Read-Modify-Write` happens as one unbreakable action.
    * **The Cost:** If Thread A is working, Thread B must **wait**. This serializes execution (turns parallel hardware into a line).

#### **3. How Atomic Add is Optimized (Hierarchical Reduction)**
* **The Problem:** If 1,000,000 threads atomically added to **one** global address, the latency would be massive (1 million waits).
* **The Solution (Divide & Conquer):** Use a tree structure (referenced in your image) to sum locally first.
    1.  **Warp Level:** Threads in a warp (32) sum their values using **Shuffle** instructions (register-to-register, zero memory access).
    2.  **Block Level:** Partial sums are written to **Shared Memory** (L1 Cache) and reduced to 1 value per block.
    3.  **Global Level:** Only the leader of each block (e.g., 1,000 leaders) performs the final **Atomic Add** to global memory.
* **Result:** Reduces contention from 1,000,000 ops $\to$ 1,000 ops.



## **1. The Mechanics of `amax` Backward**

<img src="amax_bwd.png">

When you compute `y = x.amax()`, PyTorch often discards the indices to save memory. This makes the backward pass heavier because it must "rediscover" the winners.
* **The Problem:** We need to send gradients *only* to the elements that were equal to the max.
* **The Algorithm (observed in trace):**
    1.  **`aten::eq`**: Compare Input vs. Output to find winners (creates a Boolean Mask).
    2.  **`aten::sum`**: Count the total winners (to handle ties fairly).
    3.  **`aten::to_copy`**: Cast Boolean Mask $\rightarrow$ Float. 
    4.  **`aten::mul`**: $\text{Gradient} \times (\text{Mask} / \text{Count})$.
    5.  **`aten::add_`**: Add the result to the input's `.grad` accumulator.

#### **2. `amax` vs. `max` (The Hidden Cost)**
* **`torch.max(return_indices=True)`:**
    * **Forward:** Saves the indices of the winners.
    * **Backward:** **Fast.** It creates no mask. It just uses `scatter` to send gradients directly to the saved indices.
* **`torch.amax` (or `max` without indices):**
    * **Forward:** Saves memory (drops indices).
    * **Backward:** **Slow.** Must run the 5-step "Search & Mask" algorithm described above.


#### **4. Why the Gap? (54µs)**
* **Observation:** Tiny kernels (`eq`, `cast`, `mul`) separated by white space.
* **Cause:** **Launch Latency.** Even in the backward pass (C++), asking the GPU to start 5 separate tasks takes time. The GPU finishes the math (1µs) faster than the CPU can prepare the next command (5-10µs).
* **Solution:** **Kernel Fusion.** Using `torch.compile` (Triton) would merge these 5 steps into 1 kernel, eliminating the gaps and the intermediate memory reads/writes.



## `elementwise_kernel` vs. `vectorized_elementwise_kernel`**

#### **1. The Two Worker Bees**

Whenever you perform simple math in PyTorch (e.g., `z = x * y`, `z = x + y`, `z = x.pow(2)`), the dispatcher must choose a CUDA kernel to execute the job. It generally picks between two candidates:

| Kernel Name | Alias | Characteristics |
| :--- | :--- | :--- |
| **`elementwise_kernel`** | "The Generic Worker" | **Safe but Slow.** Handles tricky shapes, complex broadcasting, and non-continuous memory. Reads/Writes 1 element at a time. |
| **`vectorized_elementwise_kernel`** | "The F1 Driver" | **Fast but Picky.** Requires perfect memory alignment. Reads/Writes 4 elements (128 bits) at a time per thread. |

#### **2. The Case Study: RMS Norm**

Consider this code snippet:

```python
# (A) Unary Math
rms = torch.rsqrt(x.pow(2).mean(-1, keepdim=True) + self.eps)

# (B) Broadcasting Math
x = x * rms 
```

**Step A: `x.pow(2)` (The Happy Path)**

  * **Input:** `x` is `(Batch, Seq, Hidden)`. Stride is `(1)` for the last dim.
  * **Output:** `x_squared` is `(Batch, Seq, Hidden)`. Stride is `(1)`.
  * **Memory Access:** The input and output line up perfectly. Index `i` in Input maps to Index `i` in Output.
  * **Dispatcher Choice:** **`vectorized_elementwise_kernel`**.
  * **Why:** PyTorch confirms that both pointers are aligned. It instructs each GPU thread to load **4 floats (128 bits)** instantly, square them in a batch, and write them back. This maximizes **Memory Coalescing**.

**Step B: `x * rms` (The Broadcast Mismatch)**

  * **Input 1:** `x` is `(Batch, Seq, Hidden)`.
  * **Input 2:** `rms` is `(Batch, Seq, 1)`.
  * **The Problem:** The `rms` tensor must be **broadcast**. For every 768 steps `x` takes in memory, `rms` must stay frozen at the same address (Stride 0).
  * **Dispatcher Choice:** **`elementwise_kernel`** (Generic).
  * **Why:** The vectorized kernel is "dumb"; it only knows how to increment *all* pointers by 4. It cannot handle the logic of "Increment Pointer A by 4, but keep Pointer B still." The generic kernel takes over, calculating the specific broadcast index for every single element, which kills the vectorization speedup.


#### **3. The Connection to Memory Coalescing**

This entire mechanism is about **Memory Coalescing**—the single most important factor in GPU programming.

  * **GPU Hardware:** GPUs access memory in "Transactions" of 32, 64, or 128 bytes. They hate reading small chunks (4 bytes).
  * **Vectorized Kernel:**
      * A warp of 32 threads reads 4 floats each.
      * Total request: $32 \times 4 \times 4 \text{ bytes} = 512 \text{ bytes}$.
      * This perfectly saturates the memory bus bandwidth.
  * **Generic Kernel (Non-Vectorized):**
      * A warp of 32 threads reads 1 float each.
      * Total request: $32 \times 4 \text{ bytes} = 128 \text{ bytes}$.
      * You are utilizing only \~25% of the potential instruction throughput for loads.

#### **4. How to Optimize (Enforcing Vectorization)**

If you see `elementwise_kernel` in your trace where you expected speed, you have three options:

1.  **`torch.compile` (The Best Way):**

      * Uses **Triton** to generate a custom kernel.
      * It "fuses" the broadcast logic. It loads the single scalar `rms` value into a fast **Register** once, then runs the full 128-bit vectorized loop over `x`, multiplying the vector by the register. Best of both worlds.

2.  **Ensure Contiguous Layouts:**

      * If the kernel is failing because of strides (e.g., `x.transpose(0,1)`), calling `x.contiguous()` will fix it.
      * *Cost:* You pay for a `copy` kernel to rearrange memory, but the subsequent math becomes vectorized.

3.  **Manual Expansion (The "Bad" Way):**

      * `rms.expand_as(x).contiguous()` physically copies the broadcasted data to match `x`'s shape.
      * This *will* trigger the vectorized kernel, but the cost of allocating extra VRAM and copying data usually outweighs the speedup. **Avoid unless necessary.**

## Softmax in Attention (MatMul vs Softmax)

<img src="softmax_in_attention.png">

<img src="compare_softmax_with_attention_mm.png">


#### **1. The FLOPs Calculation (The Theory)**
Mathematically, the "Core Attention" mechanism involves two main steps: the Dot Product ($QK^T$) and the Softmax. Let's compare their "Computational Weight" (Floating Point Operations).

* **Variables:**
    * $S$: Sequence Length (e.g., 64 or 128 in your trace)
    * $D$: Head Dimension (e.g., 64)
    * $B, H$: Batch, Heads

* **Step A: MatMul ($Q \cdot K^T$)**
    * **Operation:** Multiply $(S \times D)$ by $(D \times S)$.
    * **Math:** For every single point in the $S \times S$ output grid, you perform $2D$ operations (multiply-adds).
    * **Total FLOPs:** $2 \cdot B \cdot H \cdot S^2 \cdot \mathbf{D}$.

* **Step B: Softmax**
    * **Operation:** Normalize the $S \times S$ grid.
    * **Math:** 4 ops per element (Max, Exp, Sum, Div).
    * **Total FLOPs:** $\approx 4 \cdot B \cdot H \cdot S^2$.

* **The Ratio:**
    $$\frac{\text{MatMul FLOPs}}{\text{Softmax FLOPs}} \approx \frac{2 \cdot S^2 \cdot D}{4 \cdot S^2} \approx \frac{D}{2}$$
    * **Implication:** If your head dimension $D=64$, the **MatMul does ~32x more math** than the Softmax. You would expect it to be 32x slower.


#### **2. The Trace Reality (The Observation)**
Looking at your specific images, we see the exact opposite of what the math predicts.

* **The MatMul** (`image_bd81d5.png`):
    * **Kernel:** `aten::bmm` (inside the `computing attention` block).
    * **Visual:** A solid, compact blue block.
    * **Time:** (Based on previous traces like `image_7a285c.png`) often **~100-150 µs**.

* **The Softmax** (`image_bd8179.png`):
    * **Kernel:** Broken into multiple tiny kernels (`max`, `sum`, `exp` implied by gaps).
    * **Visual:** A wide, scattered set of blocks with white space (CPU gaps).
    * **Time:** Explicitly marked as **527 µs**.

**The Paradox:** The operation doing **32x less math** is taking **4x longer** to finish.


#### **3. The Explanation: Memory Wall & Kernel Overhead**
Why is the "light" Softmax so heavy?

**A. Memory Bandwidth (The "Taxi" Problem)**
* **MatMul:** Is **Compute Bound**. It loads $Q$ and $K$ into the chip's cache and re-uses them 64 times ($D$ times) to compute the grid. It spends its time "crunching numbers," which GPUs are built for.
* **Softmax:** Is **Memory Bound**.
    1.  Kernel 1 (Max): Read entire $S^2$ matrix from VRAM $\to$ Write Max.
    2.  Kernel 2 (Exp): Read entire $S^2$ matrix $\to$ Write Exponentiated matrix.
    3.  Kernel 3 (Sum): Read entire $S^2$ matrix $\to$ Write Sums.
    4.  Kernel 4 (Div): Read entire $S^2$ matrix $\to$ Write Final.
    * **Result:** You are shuttling the *entire* attention matrix back and forth to VRAM 4 times. The GPU cores are sitting idle, waiting for data.

**B. Kernel Launch Overhead (The Gaps)**
* In `image_bd8179.png`, look at the white space between the blue blocks under "computing softmax."
* Since your Softmax is unfused (standard PyTorch implementation), the CPU must tell the GPU to launch "Max," then wait, then launch "Exp," then wait.
* For small sequence lengths (like $S=64$), the time it takes the CPU to say "Go" (Launch Latency ~10µs) is longer than the time it takes the GPU to do the math (~1µs). You are mostly profiling the CPU's sluggishness.

#### **4. The Fix: Flash Attention**
This specific visual—a wide, multi-kernel Softmax taking longer than the MatMul—is the exact motivation for **Flash Attention**.
* **Flash Attention** fuses the MatMul and Softmax into a single kernel.
* It computes the Softmax *inside* the fast SRAM (cache) immediately after the MatMul, without ever writing the huge $S^2$ matrix to main memory.
* **Result:** The 527µs Softmax block effectively vanishes, merging into the MatMul block.


## **Optimizer Mechanics & `multi_tensor_apply`**

<img src="optimizer-multi-tensor.png">

#### **1. The First Step: "Lazy Initialization" & The `cudaMalloc` Confusion**

You observed that the first `optimizer.step()` took **8.2ms** while subsequent steps were instant. This is **Lazy Initialization**.

  * **What happens:** PyTorch optimizers (like AdamW) do not create momentum buffers ($m_t$) or variance buffers ($v_t$) when you initialize the class. They wait until the *first time* they see a gradient for a specific parameter.
  * **The Bottleneck:** The CPU must request memory for every single parameter (e.g., if you have 100 layers, that is 200 buffers for weights+biases).
  * **The `cudaMalloc` Paradox:**
      * *Question:* "Isn't `cudaMalloc` a GPU operation?"
      * *Answer:* The *allocation* happens on VRAM, but the **Management** happens on the CPU.
      * *The CPU's Job:* The CPU executes the C++ function `cudaMalloc`. It has to pause, talk to the CUDA Driver, find a free page in the GPU's virtual memory table, update the page table, and return a pointer.
      * *The Result:* The huge 8.2ms block you see is mostly the **CPU** running this administrative code. The GPU is largely idle (showing white space) waiting for the CPU to finish figuring out where the memory lives.

#### **2. `multi_tensor_apply`: The Solution to Launch Overhead**

Once memory is allocated, how do we update 500 different weight tensors scattered across memory?

  * **The Naive Way (Slow):**
    ```python
    for p in parameters:
        # Launch 1 kernel per parameter
        # Cost: 500 * (10µs Launch Latency) = 5ms Overhead!
        p.grad = ...
    ```
  * **The `multi_tensor_apply` Way (Fast):**
    Instead of launching 500 kernels, PyTorch builds a **List of Pointers** on the CPU: `[Ptr_W1, Ptr_B1, Ptr_W2, ...]`.
    It sends this *list* to the GPU in a **single kernel launch**.
      * **The Kernel:** A large grid of CUDA threads launches. Block 1 grabs `Ptr_W1` and updates it. Block 2 grabs `Ptr_B1`.
      * **The Gain:** You pay the 10µs launch tax **once** instead of 500 times.

#### **3. Fused Adam Implementation**

Modern PyTorch Adam uses **Kernel Fusion** to maximize memory bandwidth. It does not calculate momentum, then variance, then weights separately.

  * **Unfused (Bad - 3 trips to memory):**
    1.  Read $g$, Read $m$ $\rightarrow$ Write $m_{new}$.
    2.  Read $g$, Read $v$ $\rightarrow$ Write $v_{new}$.
    3.  Read $m_{new}$, Read $v_{new}$, Read $W$ $\rightarrow$ Write $W_{new}$.
  * **Fused (Good - 1 trip to memory):**
    The kernel loads $g, m, v, W$ into fast Registers **once**.
    ```cpp
    // Pseudo-CUDA
    float g = load(grad_ptr);
    float m = load(mom_ptr);
    float v = load(var_ptr);

    // Do all math in registers (SRAM)
    m = beta1 * m + (1-beta1) * g;
    v = beta2 * v + (1-beta2) * g^2;
    w = w - lr * m / (sqrt(v) + eps);

    // Write back
    store(mom_ptr, m);
    store(var_ptr, v);
    store(weight_ptr, w);
    ```
    This is why you see one solid bar on the timeline: it is performing the update logic for all 3 states simultaneously.

#### **4. Faster Alternatives (Beyond `multi_tensor`)**

Why isn't `multi_tensor_apply` perfect? Because the memory is still **Scattered** (fragmented). The GPU prefers reading one massive contiguous block.

  * **Foreach Kernels (`_foreach`):** A newer PyTorch feature that is slightly faster than `multi_tensor` for certain ops, utilizing more optimized vertical fusion.
  * **APEX / FusedAdam (NVIDIA):**
      * Often performs a **"Flattening"** trick. It views all your parameters as one giant 1GB array of floats.
      * This allows it to launch a single **perfectly coalesced** kernel that marches from address 0 to $N$ without jumping around memory addresses.
  * **CUDA Graphs:** The ultimate optimizer. It "records" the CPU's launch commands (including the pointer lists) and replays them instantly, removing even the overhead of building the pointer list.

### What does these new triton kernel names look like?


### **1. The Kernel Naming Decoder (Recap)**

When `torch.compile` (using Triton) generates kernels, it names them based on the **loop structure** and **data dependency**.

#### A. `triton_poi` (Pointwise)
* **Meaning:** **"Pointwise"**
* **What it does:** Every thread works on a single data point completely independently. There is no communication between threads.
* **DL Operations:**
    * Activations (ReLU, GELU, SiLU)
    * Element-wise math (`+`, `-`, `*` like in a residual connection)
    * Casting (FP32 -> FP16)
* **Bottleneck:** **Memory Bandwidth.** Since the math is trivial, the GPU spends all its time reading/writing VRAM.
* **Optimization Goal:** These are what typically get "fused" together. Ideally, you want one giant `triton_poi` kernel that does `Load -> Add -> Mul -> Act -> Store` in a single pass.

#### B. `triton_red` (Reduction)
* **Meaning:** **"Reduction"**
* **What it does:** Threads need to combine values to produce a smaller output (Many-to-One or Many-to-Few).
* **DL Operations:**
    * `Sum`, `Mean`, `Max`, `Min`.
    * Standard Cross Entropy Loss calculation.
* **Bottleneck:** **Synchronization.** Threads must talk to each other ("I have 5, what do you have?") to compute the total.

#### C. `triton_per` (Persistent Reduction)
* **Meaning:** **"Persistent"** (often Persistent Reduction)
* **What it does:** This is a special, highly optimized version of a reduction used when the data size (e.g., the hidden dimension $d=4096$) fits entirely inside the GPU's fast L1/Shared Memory cache.
* **How it works:** Instead of loading data, reducing a chunk, saving it, and loading the next chunk, the CUDA core keeps the data "persistent" in its fastest cache and reduces it in one go.
* **DL Operations:**
    * **Normalization:** LayerNorm, RMSNorm.
    * **Softmax:** (The reduction across the vocab or sequence dimension).
* **Why it matters:** Seeing `triton_per` is usually a **good sign**. It means the compiler successfully identified that it could use this specialized, ultra-fast cache strategy.

Before diving into the code, here is the quick refresh on the prefixes Triton uses, which tell you the *strategy* the compiler chose:

  * **`triton_poi` (Pointwise):** Independent math on every element (e.g., `x + y`).
  * **`triton_per` (Persistent Reduction):** A "smart" reduction where the data for a row fits entirely in the GPU's fastest cache (L1/Shared). It loads once, reduces, and exits. Very fast.
  * **`triton_red` (Standard Reduction):** A general-purpose reduction (sum, max, mean) used when data is too large for the "Persistent" trick or when synchronization is required across blocks.


### Mapping the Code to the Kernels
```python
def cross_entropy_loss(logits: torch.Tensor, target: torch.Tensor):
    xc = logits.gather(-1, target[..., None])
    max_x = torch.amax(logits, dim=1, keepdim=True)
    lse = max_x + torch.log(torch.sum(torch.exp(logits - max_x), dim=-1, keepdim=True))
    return -torch.mean(xc - lse)
```

<img src="triton-kernel-names.png">


#### **Kernel A: `triton_per_fused_amax_0`**

  * **Python Code:**
    ```python
    max_x = torch.amax(logits, dim=1, keepdim=True)
    ```
  * **Operations Fused:** Just the `amax`.
  * **Why `per`?** The compiler noticed that finding the max of your dimension (likely the vocab size or sequence length) fits into the GPU's fast cache. It keeps the running "max value" in registers without writing intermediate results back to main memory.

#### **Kernel B: `triton_red_fused_exp_sub_sum_1`**

```python
# The inner part of the LogSumExp trick
... torch.sum(torch.exp(logits - max_x), dim=-1, keepdim=True)
```
**Operations Fused:**
  1.  **`sub`**: `logits - max_x` (Subtract max for numerical stability)
  2.  **`exp`**: `torch.exp(...)` (Exponentiate the result)
  3.  **`sum`**: `torch.sum(...)` (Sum them up)

**The Gain:** In eager mode, `logits - max_x` would create a giant temporary tensor, then `exp` would read that and create *another* giant tensor. This kernel does `load -> sub -> exp -> sum` in a single pass through the chip.

#### **Kernel C: `triton_red_fused_add_gather_log_mean_sub_2`**

```python
# 1. Finish LSE calculation
lse = max_x + torch.log(...)

# 2. Get the true class score
xc = logits.gather(-1, target[..., None])

# 3. Final Loss
return -torch.mean(xc - lse)
```
**Operations Fused:**
  1.  **`log`**: Computes the log of the sum from Kernel B.
  2.  **`add`**: Adds `max_x` back to get the final `lse`.
  3.  **`gather`**: lookup the specific logic for the target class (`xc`).
  4.  **`sub`**: `xc - lse`.
  5.  **`mean`**: Reduces everything to a single scalar loss value.

**The Magic:** This is the most impressive fusion. It combined indexing (`gather`), arithmetic (`add`, `sub`, `log`), and a global reduction (`mean`) into one massive kernel. This prevents the GPU from having to write the full `xc` or `lse` tensors to memory; it just computes the final scalar loss directly.

| **Log & Add** | 2 Kernels (`log`, `add`) | **Kernel 3** (`red_fused_...`) |
| **Gather Targets** | 1 Kernel (`gather`) | (Fused into Kernel 3) |
| **Diff & Mean** | 2 Kernels (`sub`, `mean`) | (Fused into Kernel 3) |
| **Total Launches** | **\~9 Launches** | **3 Launches** |
